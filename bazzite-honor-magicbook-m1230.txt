ШАГ 5. ПРОВЕРЯЕМ ACPI I2C_DEVT. ЭТО ОБЯЗАТЕЛЬНЫЙ SAFETY CHECK
======================================================================

Мы НЕ копируем AML вслепую.

Остаёмся здесь:

Вставь блок:

LIVE=""

for f in /sys/firmware/acpi/tables/SSDT*; do
    OEM=$(sudo dd if="$f" bs=1 skip=16 count=8 status=none 2>/dev/null | tr -d '\0 ')

    if [[ "$OEM" == "I2C_DEVT" ]]; then
        LIVE="$f"
        break
    fi
done

if [[ -z "$LIVE" ]]; then
    echo "STOP: I2C_DEVT не найдена. НЕ продолжай со следующим шагом."
else
    LIVE_MD5=$(sudo md5sum "$LIVE" | awk '{print $1}')
    REF_MD5=$(md5sum dump/acpi/zqc-p/SSDT27_orig.aml | awk '{print $1}')

    echo "LIVE TABLE: $LIVE"
    echo "LIVE MD5 : $LIVE_MD5"
    echo "REPO MD5 : $REF_MD5"

    if [[ "$LIVE_MD5" == "$REF_MD5" ]]; then
        echo "OK: заводская I2C_DEVT полностью совпадает с reference."
    else
        echo "STOP: таблицы отличаются. AML НЕ устанавливаем и дальше НЕ продолжай."
    fi
fi

Только если в конце было OK — продолжаем.

ВАЖНО ДЛЯ BAZZITE:
если build проходит, но install падает с:

OSError: [Errno 30] Read-only file system: '/usr/lib/udev/rules.d/70-libfprint-2.rules'
install failed

это не ошибка fingerprint patch. Bazzite держит /usr read-only, а upstream
libfprint пытается поставить udev rule именно туда.

Исправляем local installer один раз так:

python3 - <<'PY'
from pathlib import Path

p = Path("patch/fingerprint/install.sh")
s = p.read_text()

old = '''    ninja -C "$GITDIR/build" >/dev/null || die "build failed"
    ninja -C "$GITDIR/build" install >/dev/null || die "install failed"
'''

new = '''    ninja -C "$GITDIR/build" >/dev/null || die "build failed"

    # Bazzite/Fedora Atomic: /usr is read-only. Stage the Meson install first,
    # then copy the private /opt prefix and place the generated udev rule in /etc.
    STAGE="${WORK}/stage"
    mkdir -p "$STAGE"
    DESTDIR="$STAGE" ninja -C "$GITDIR/build" install >/dev/null \
        || die "staged install failed"

    rm -rf "$PREFIX"
    [[ -d "$STAGE$PREFIX" ]] \
        || die "staged prefix missing: $STAGE$PREFIX"
    install -d "$(dirname "$PREFIX")"
    cp -a "$STAGE$PREFIX" "$PREFIX"

    UDEV_RULE="$STAGE/usr/lib/udev/rules.d/70-libfprint-2.rules"
    if [[ -f "$UDEV_RULE" ]]; then
        install -Dm644 "$UDEV_RULE" /etc/udev/rules.d/70-libfprint-2.rules
        udevadm control --reload
        udevadm trigger --subsystem-match=usb --action=add 2>/dev/null || true
    fi
    restorecon -RF "$PREFIX" /etc/udev/rules.d/70-libfprint-2.rules \
        >/dev/null 2>&1 || true
'''

if old not in s:
    raise SystemExit("STOP: expected installer block not found; do not patch blindly")

p.write_text(s.replace(old, new, 1))
print("OK: fingerprint installer adapted for Bazzite read-only /usr")
PY

Фиксируем эту Bazzite-адаптацию в нашей local branch:

ШАГ 13. ПРОВЕРЯЕМ DSC В ТЕКУЩЕМ OGC KERNEL

В OGC kernel есть writable debugfs switch для force DSC.

Сначала убеждаемся, что debugfs доступен:

sudo mountpoint -q /sys/kernel/debug || sudo mount -t debugfs debugfs /sys/kernel/debug

Находим DSC file:

DSC_FILE=$(sudo find /sys/kernel/debug/dri \
  -path '*/eDP-*/i915_dsc_fec_support' \
  -print -quit)

Он НЕ должен быть пустым.

Смотрим:

sudo cat "$DSC_FILE"

Нужно увидеть как минимум:

DSC_Sink_Support: yes

До force обычно будет:

DSC_Enabled: no
Force_DSC_Enable: no

Если DSC_Sink_Support НЕ yes — СТОП, force не делаем.

ШАГ 14. ДЕЛАЕМ DSC АВТОМАТИЧЕСКИМ ПРИ КАЖДОМ BOOT
======================================================================

Создаём helper:

sudo install -d -m755 /usr/local/lib/honor

sudo tee /usr/local/lib/honor/force-dsc.sh >/dev/null <<'EOF'
#!/usr/bin/bash
set -euo pipefail

mountpoint -q /sys/kernel/debug || mount -t debugfs debugfs /sys/kernel/debug

for _ in $(seq 1 300); do
    DSC_FILE=$(find /sys/kernel/debug/dri \
      -path '*/eDP-*/i915_dsc_fec_support' \
      -print -quit 2>/dev/null || true)

    if [[ -n "$DSC_FILE" && -w "$DSC_FILE" ]]; then
        if ! grep -q 'DSC_Sink_Support: yes' "$DSC_FILE"; then
            echo "HONOR: panel does not report DSC support" >&2
            exit 1
        fi

        echo 1 > "$DSC_FILE"
        exit 0
    fi

    sleep 0.05
done

echo "HONOR: i915_dsc_fec_support not found" >&2
exit 1
EOF

sudo chmod 755 /usr/local/lib/honor/force-dsc.sh

Создаём service:

sudo tee /etc/systemd/system/honor-force-dsc.service >/dev/null <<'EOF'
[Unit]
Description=Force DSC on HONOR ZQC-P internal eDP panel
After=systemd-modules-load.service
Before=display-manager.service

[Service]
Type=oneshot
ExecStart=/usr/local/lib/honor/force-dsc.sh
RemainAfterExit=yes

[Install]
WantedBy=multi-user.target
EOF

Включаем:

Пока reboot не делаем — сначала доделаем update protection.


======================================================================
ШАГ 15. ДЕЛАЕМ БЕЗОПАСНОЕ ОБНОВЛЕНИЕ HONOR SOURCE TREE
======================================================================

Сам source tree НЕ должен самовольно переустанавливать тебе фиксы.
Он нужен только если когда-нибудь вручную захочешь обновить upstream.

НИКОГДА не делай в нём обычный git pull.

Создаём безопасный updater:

sudo tee /usr/local/bin/honor-source-update >/dev/null <<'EOF'
#!/usr/bin/bash
set -euo pipefail

REPO=/var/opt/honor-magicbook-linux
cd "$REPO"

if [[ "$(git branch --show-current)" != "m1230-bazzite" ]]; then
    echo "STOP: expected branch m1230-bazzite" >&2
    exit 1
fi

if [[ -n "$(git status --porcelain)" ]]; then
    echo "STOP: working tree dirty. Ничего не обновляю." >&2
    git status --short
    exit 1
fi

git branch -f honor-last-good HEAD
git fetch --prune origin

if git rebase origin/main; then
    echo
    echo "HONOR source tree updated."
    echo "ВАЖНО: установленные системные фиксы автоматически НЕ менялись."
    echo "Новый installer запускай только вручную после проверки."
else
    echo
    echo "Upstream конфликтует с нашим M1230 commit."
    echo "Отменяю rebase и сохраняю старое рабочее состояние."
    git rebase --abort || true
    exit 1
fi
EOF

sudo chmod 755 /usr/local/bin/honor-source-update

Проверка:

command -v honor-source-update

В БУДУЩЕМ исходники обновлять только так:

honor-source-update

ШАГ 16. ДЕЛАЕМ HEALTH-CHECK ПОСЛЕ КАЖДОГО BOOT

fi

ШАГ 17. ЧИСТИМ LAYERED BUILD-ПАКЕТЫ, НО НЕ ЛОМАЕМ KBDLIGHT REBUILD
======================================================================

ВАЖНО: после добавления honor-zqcp-kbdlight НЕЛЬЗЯ удалять вообще все build
tools из temp-layered.txt.

Наш service /usr/local/lib/honor/kbdlight-build-load.sh после обновления kernel
при необходимости сам пересобирает honor_zqcp_kbdlight.ko. Для этого ему
нужны как минимум:

- gcc
- make

matching kernel-devel Bazzite сейчас поставляет вместе со своим OGC kernel.

Git тоже оставляем: он нужен honor-source-update.

Остальные build-only пакеты после успешной установки micmute/touchpad/fingerprint
в runtime не нужны. Их можно удалить, чтобы уменьшить rpm-ostree layering.

Посмотреть, что мы временно добавляли:

cat /var/lib/honor/temp-layered.txt

Безопасно удалить всё из этого списка КРОМЕ gcc и make:

mapfile -t ALL_TEMP < /var/lib/honor/temp-layered.txt
REMOVE=()

for p in "${ALL_TEMP[@]}"; do
    case "$p" in
        gcc|make)
            echo "KEEP: $p (нужен для автоматической пересборки kbdlight)"
            ;;
        *)
            REMOVE+=("$p")
            ;;
    esac
done

if (( ${#REMOVE[@]} )); then
    sudo rpm-ostree uninstall "${REMOVE[@]}"
else
    echo "Нечего удалять."
fi

Отдельно libbpf-devel, если мы layer'или его позже для HID-BPF, в runtime тоже
не нужен: уже установленные CO-RE .bpf.o работают без него.

Проверить:

rpm -q libbpf-devel >/dev/null 2>&1 && echo "libbpf-devel layered/present"

Если он был добавлен нами через rpm-ostree, его можно снять:

sudo rpm-ostree uninstall libbpf-devel

Если rpm-ostree скажет, что пакет не requested/layered — просто ничего не делай.

Проверяем pending deployment:

rpm-ostree status -v

Почему вообще чистим:
Bazzite официально предупреждает, что лишние rpm-ostree layered packages могут
замедлять обновления и иногда блокировать upgrade/rebase из-за dependency
conflicts. Поэтому держим только то, что реально нужно host-системе.

КАК ТЕПЕРЬ ОБНОВЛЯТЬ BAZZITE
======================================================================

Обычный Bazzite update делаешь ШТАТНО, как всегда.

После update:
1. перезагружаешься;
2. ждёшь примерно минуту;
3. выполняешь:

cat /var/lib/honor/health-last.txt

Если:

ничего делать не надо.

Почему наши вещи должны переживать Bazzite updates:
- ACPI AML находится в /etc;
- dracut config находится в /etc;
- rpm-ostree local initramfs включён постоянно;
- xe.enable_psr=1 хранится как karg;
- HID-BPF объекты живут в /etc/udev-hid-bpf;
- micmute имеет boot re-apply service;
- DSC имеет собственный systemd service;
- fingerprint SDCP library живёт в /opt;
- его ld.so config живёт в /etc;
- source tree живёт в /var/opt;
- мы НЕ подменяем kernel modules;
- мы НЕ собираем xe.ko под конкретную версию kernel.

Именно поэтому kernel update не должен заставлять нас пересобирать половину
ноутбука заново.

======================================================================
ДОПОЛНЕНИЕ: ПОДСВЕТКА КЛАВИАТУРЫ НА ZQC-P / M1230
======================================================================

ВАЖНО: KDE действительно показывает ползунок "Подсветка клавиатуры", но на
ZQC-P это НЕ означает, что управление работает.

Текущий in-tree huawei-wmi создаёт интерфейс huawei::kbd_backlight / UPower
KbdBacklight, поэтому KDE рисует ползунок. Однако на ZQC-P запись уровня через
этот путь заканчивается -ENODEV и физическая яркость не меняется.

Это прямо задокументировано в upstream HONOR Linux repo:
docs/LIMITATIONS.md и docs/hardware/zqc-p.md.

То есть:
- KDE slider существует;
- UPower KbdBacklight существует;
- реальная подсветка через текущий huawei-wmi НЕ меняется.

Это НЕ ограничение firmware. В DSDT ZQC-P есть EC field KBBL at offset 0x41.
Известное отображение:
- 0x04 = off
- 0x02 = low
- 0x03 = high
- 0x01 = latch current level

Для sibling FMB-P уже существует GPL driver honor-fmbp-kbdlight, который
управляет тем же EC полем. Но на M1230 его нельзя ставить вслепую:
он DMI-bound к FMB-P, а на ZQC-P уже существует мёртвый huawei::kbd_backlight,
поэтому сначала нужен отдельный ZQC-P/M1230-safe вариант без конфликта LED name.

Пока этот отдельный драйвер не добавлен и не протестирован:
keyboard backlight slider в KDE считать НЕРАБОЧИМ.

======================================================================
ДОПОЛНЕНИЕ: РЕАЛЬНОЕ УПРАВЛЕНИЕ ПОДСВЕТКОЙ КЛАВИАТУРЫ НА M1230
======================================================================

На ZQC-P штатный KDE/UPower slider может существовать, но через текущий
huawei-wmi физическую яркость не менять.

Для M1230 добавлен отдельный GPL LED-class driver:
honor-zqcp-kbdlight/

Он основан на drphilth honor-fmbp-kbdlight и адаптирован только под:
- HONOR
- ZQC-P
- board M1230

Перед загрузкой installer дополнительно проверяет, что текущий DSDT содержит
KBBL/GKBM/SKBM. Модуль использует документированный EC KBBL offset 0x41:
- 0x04 off
- 0x02 low
- 0x03 high
- 0x01 latch

Он регистрирует отдельный LED:

/sys/class/leds/honor::kbd_backlight

и не меняет физическую яркость при самой загрузке модуля.

Установка из my-dotfiles:

rm -rf /tmp/my-dotfiles
git clone --depth 1 https://github.com/pluseight8/my-dotfiles.git /tmp/my-dotfiles
sudo bash /tmp/my-dotfiles/honor-zqcp-kbdlight/install-bazzite.sh

Проверка напрямую:

echo 0 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
echo 1 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
echo 2 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness

На M1230 подтверждено: прямые записи 0/1/2 в
/sys/class/leds/honor::kbd_backlight/brightness ФИЗИЧЕСКИ меняют подсветку
клавиатуры. Значит EC mapping и наш honor_zqcp_kbdlight driver работают.

Если после установки прямой sysfs test работает, а KDE slider всё ещё ничего
не меняет, проблема уже не в EC driver, а в том, что UPower/PowerDevil ещё
держат старый backend.

Перезапусти их:

sudo systemctl restart upower.service
systemctl --user restart plasma-powerdevil.service

После этого снова проверь ползунок KDE.

Если slider всё ещё мёртвый, собери диагностику:

busctl tree org.freedesktop.UPower | grep -i KbdBacklight
ls -1 /sys/class/leds

Если эти три значения реально меняют подсветку, KDE/UPower можно перезапустить:

sudo systemctl restart upower.service

После этого при необходимости один раз выйти из KDE и войти обратно.

Для обновлений Bazzite:
source и собранные модули лежат в /var/lib/honor.
honor-zqcp-kbdlight.service при boot проверяет текущий kernel и автоматически
пересобирает модуль, если kernel release изменился и matching kernel-devel
доступен.

======================================================================
ДИАГНОСТИКА: HONOR::KBD_BACKLIGHT ПРОПАЛ ПОСЛЕ УСТАНОВКИ
======================================================================

Если прямой sysfs test раньше работал:

echo 0 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
echo 2 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness

но позже `ls -1 /sys/class/leds` больше НЕ показывает
`honor::kbd_backlight`, сначала НИЧЕГО не переустанавливаем.

Собрать состояние service/module/journal:

systemctl status honor-zqcp-kbdlight.service --no-pager -l
lsmod | grep honor_zqcp || true
sudo journalctl -u honor-zqcp-kbdlight.service -b --no-pager -n 50

Также проверить, существует ли LED сейчас:

test -d /sys/class/leds/honor::kbd_backlight \
  && echo "honor::kbd_backlight: PRESENT" \
  || echo "honor::kbd_backlight: MISSING"

Эти команды нужны, чтобы понять, почему модуль, который уже доказанно умеет
управлять физической подсветкой на M1230, не остаётся загруженным/не создаёт
LED после последующих действий или boot.

ВАЖНО ДЛЯ ЭТОГО ГАЙДА:
все следующие диагностические и исправляющие команды по этой установке должны
сначала добавляться сюда в GitHub, а уже потом выполняться на ноутбуке.

  && echo "honor::kbd_backlight: PRESENT" \
  || echo "honor::kbd_backlight: MISSING"

Если PRESENT, сразу проверяем физическую подсветку:

echo 0 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
sleep 2
echo 2 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness

После этого перезапускаем userspace power stack:

sudo systemctl restart upower.service
systemctl --user restart plasma-powerdevil.service

Причина этого шага:
первый вариант install-bazzite.sh делал `systemctl enable`, а затем запускал
build/load helper напрямую. То есть module мог быть загружен, но сам unit не
становился active. Теперь service должен быть ENABLED + ACTIVE, чтобы systemd
держал состояние и корректно поднимал driver после boot.

======================================================================
ДИАГНОСТИКА: HONOR-ZQCP-KBDLIGHT.SERVICE FAILED ПРИ ENABLE --NOW
======================================================================

Если команда:

sudo systemctl enable --now honor-zqcp-kbdlight.service

заканчивается сообщением:

Job for honor-zqcp-kbdlight.service failed because the control process exited with error code

НЕ переустанавливаем драйвер и НЕ меняем EC вручную.

Сначала собираем точную причину:

systemctl status honor-zqcp-kbdlight.service --no-pager -l
sudo journalctl -xeu honor-zqcp-kbdlight.service --no-pager -n 100

Потом отдельно запускаем helper вручную с shell trace:

sudo bash -x /usr/local/lib/honor/kbdlight-build-load.sh

И проверяем ключевые пути:

uname -r
ls -ld /lib/modules/"$(uname -r)"/build
ls -l /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko 2>/dev/null || true
lsmod | grep honor_zqcp || true
ls -1 /sys/class/leds

ВАЖНО:
ошибка systemd здесь ещё не означает, что EC driver сломан. Она означает только,
что ExecStart helper вернул ненулевой код. По trace/journal определяем конкретный
шаг: kernel-devel, rebuild, insmod или появление LED device.

======================================================================
ДИАГНОСТИКА: INSMOD -> OPERATION NOT PERMITTED
======================================================================

Если journal/helper показывает примерно это:

insmod: ERROR: could not insert module .../honor_zqcp_kbdlight.ko: Operation not permitted

при этом:
- matching /lib/modules/$(uname -r)/build существует;
- honor_zqcp_kbdlight.ko успешно собран;
- lsmod не показывает honor_zqcp_kbdlight;

то наиболее вероятная причина — Secure Boot / kernel lockdown не разрешает
загрузку нашего неподписанного out-of-tree .ko.

НЕ отключаем Secure Boot вслепую. Сначала подтверждаем:

mokutil --sb-state || true
cat /sys/kernel/security/lockdown 2>/dev/null || true
sudo dmesg | grep -iE 'lockdown|secure boot|verification|module.*signature|unsigned|key.*rejected' | tail -n 80

Также смотрим подпись модуля:

modinfo -F signer /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko 2>/dev/null || true
modinfo -F sig_id /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko 2>/dev/null || true

Если signer пустой, а Secure Boot/lockdown включён и dmesg говорит про
verification/signature/key rejection, причина подтверждена: модуль надо
подписать доверенным ключом, а не пересобирать заново и не трогать EC mapping.

До подтверждения ничего в BIOS не меняем.

======================================================================
ДИАГНОСТИКА: SECURE BOOT ВЫКЛЮЧЕН, НО SYSTEMD INSMOD ДАЁТ EPERM
======================================================================

Если предыдущая проверка показывает:
- SecureBoot disabled;
- lockdown = [none];
- signer у honor_zqcp_kbdlight.ko пустой;
- kernel разрешает другие неподписанные модули с tainting;

то гипотеза про Secure Boot НЕ подтверждена.

Так как первый install-bazzite.sh успешно загружал тот же .ko из root shell,
а honor-zqcp-kbdlight.service позже получает "Operation not permitted",
проверяем две вещи:
1) не отключена ли загрузка модулей глобально;
2) не блокирует ли загрузку SELinux/systemd context при попытке читать .ko из
   /var/lib/honor.

Сначала:

cat /proc/sys/kernel/modules_disabled
getenforce

Потом контексты файлов:

ls -lZ /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko
ls -lZ /usr/local/lib/honor/kbdlight-build-load.sh
ls -lZ /etc/systemd/system/honor-zqcp-kbdlight.service

Проверяем SELinux AVC:

sudo ausearch -m AVC,USER_AVC -ts boot 2>/dev/null \
  | grep -Ei 'kbdlight|honor_zqcp|insmod|module|var/lib/honor' \
  | tail -n 100 || true

sudo journalctl -k -b --no-pager \
  | grep -Ei 'avc|selinux|denied|kbdlight|honor_zqcp' \
  | tail -n 100 || true

И главный контрольный тест: грузим ТОТ ЖЕ .ko вручную из обычного sudo shell и
сразу читаем последние kernel messages:

KO="/var/lib/honor/kbdlight/$(uname -r)/honor_zqcp_kbdlight.ko"
sudo insmod "$KO"; RC=$?
echo "insmod rc=$RC"
lsmod | grep honor_zqcp || true
ls -1 /sys/class/leds | grep -E 'honor|huawei|kbd' || true
sudo dmesg | tail -n 100

Интерпретация:
- modules_disabled = 1 -> kernel уже глобально запретил новые module loads;
- manual sudo insmod WORKS, а systemd service FAILS -> почти наверняка
  SELinux/unit-context/path-label issue;
- manual sudo insmod тоже FAILS -> точную причину берём из последних dmesg;
- после успешного manual insmod должен снова появиться honor::kbd_backlight.

НЕ отключать SELinux и НЕ менять Secure Boot ради теста.

======================================================================
FIX: SELINUX БЛОКИРУЕТ KBDLIGHT .KO ИЗ /VAR/LIB/HONOR
======================================================================

Подтверждённая причина на M1230:

- kernel.modules_disabled = 0
- SELinux = Enforcing
- ручной sudo insmod того же .ko работает (insmod rc=0)
- honor_zqcp_kbdlight появляется в lsmod
- /sys/class/leds/honor::kbd_backlight появляется
- journal/ausearch показывает AVC denial:
  comm="insmod"
  path="/var/lib/honor/kbdlight/.../honor_zqcp_kbdlight.ko"
  scontext=system_u:system_r:systemd_t
  tcontext=system_u:object_r:var_lib_t
  denied { module_load }

То есть сам модуль исправен. Systemd service падает потому, что .ko лежит под
/var/lib/honor и имеет SELinux label var_lib_t, из которого systemd_t не может
делать module_load.

НЕ отключаем SELinux.

Сначала смотрим SELinux type обычного kernel module в /lib/modules:

REF_MODULE="$(find /lib/modules/"$(uname -r)" -type f -name '*.ko*' -print -quit)"
echo "$REF_MODULE"
ls -lZ "$REF_MODULE"

Если type у reference module = modules_object_t, присваиваем тот же type нашему
module tree:

sudo chcon -R -t modules_object_t /var/lib/honor/kbdlight

Проверяем:

ls -lZ /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko

Если honor_zqcp_kbdlight уже загружен вручную, выгружаем его перед повторным
стартом service:

sudo rmmod honor_zqcp_kbdlight 2>/dev/null || true

Теперь:

sudo systemctl restart honor-zqcp-kbdlight.service
systemctl status honor-zqcp-kbdlight.service --no-pager -l

Проверяем:

lsmod | grep honor_zqcp || true
ls -1 /sys/class/leds | grep -E 'honor|huawei|kbd' || true

И физический тест:

echo 0 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
sleep 2
echo 2 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness

ВАЖНО:
chcon подтверждает/fixes проблему прямо сейчас, но label может потеряться, если
файл будет создан заново при rebuild. Поэтому после подтверждения installer/
rebuild helper должен сам ставить корректный SELinux type на новый .ko.

======================================================================
ПОДТВЕРЖДЕНО: REFERENCE KERNEL MODULE ИМЕЕТ modules_object_t
======================================================================

На M1230/Bazzite проверено: обычный kernel module из
/lib/modules/$(uname -r) имеет SELinux type:

system_u:object_r:modules_object_t:s0

Значит honor_zqcp_kbdlight.ko под /var/lib/honor должен получить тот же type.

Применяем к уже собранному module tree:

sudo chcon -R -t modules_object_t /var/lib/honor/kbdlight

Проверяем конкретный .ko:

ls -lZ /var/lib/honor/kbdlight/"$(uname -r)"/honor_zqcp_kbdlight.ko

Если модуль сейчас загружен после ручного sudo insmod, выгружаем:

sudo rmmod honor_zqcp_kbdlight 2>/dev/null || true

Теперь запускаем именно systemd service:

sudo systemctl restart honor-zqcp-kbdlight.service

Проверяем:

systemctl status honor-zqcp-kbdlight.service --no-pager -l
lsmod | grep honor_zqcp || true
ls -1 /sys/class/leds | grep -E 'honor|huawei|kbd' || true

Если service active и honor::kbd_backlight присутствует, физический тест:

echo 0 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness
sleep 2
echo 2 | sudo tee /sys/class/leds/honor::kbd_backlight/brightness

После успешного теста обновляем локальную установку installer'ом из my-dotfiles,
потому что актуальный install-bazzite.sh теперь сам делает:

chcon -t modules_object_t "$KO"

после каждой сборки нового .ko. Это нужно, чтобы fix не сломался после будущего
kernel update.

Обновление установленного helper/service из GitHub:

rm -rf /tmp/my-dotfiles
git clone --depth 1 https://github.com/pluseight8/my-dotfiles.git /tmp/my-dotfiles
sudo bash /tmp/my-dotfiles/honor-zqcp-kbdlight/install-bazzite.sh

======================================================================
KDE SLIDER: DRIVER РАБОТАЕТ, НО POWERDEVIL ЕЩЁ НЕ УПРАВЛЯЕТ ИМ
======================================================================

Состояние, подтверждённое на M1230:
- honor-zqcp-kbdlight.service = active (exited)
- honor_zqcp_kbdlight загружен
- /sys/class/leds/honor::kbd_backlight существует
- прямые записи 0/1/2 физически меняют подсветку
- KDE slider при этом может всё ещё ничего не делать

ВАЖНО: после того как LED наконец появился и стал постоянным, UPower и
PowerDevil надо перезапустить ЕЩЁ РАЗ. Раньше они перезапускались в момент,
когда honor::kbd_backlight уже успевал исчезнуть.

Сначала:

sudo systemctl restart upower.service
systemctl --user restart plasma-powerdevil.service
sleep 2

Проверяем, к какому sysfs LED реально привязан legacy UPower object:

busctl get-property org.freedesktop.UPower \
  /org/freedesktop/UPower/KbdBacklight \
  org.freedesktop.UPower.KbdBacklight NativePath

Проверяем его значения:

busctl call org.freedesktop.UPower \
  /org/freedesktop/UPower/KbdBacklight \
  org.freedesktop.UPower.KbdBacklight GetBrightness

busctl call org.freedesktop.UPower \
  /org/freedesktop/UPower/KbdBacklight \
  org.freedesktop.UPower.KbdBacklight GetMaxBrightness

Прямой тест ЧЕРЕЗ UPower DBus, а не sysfs:

busctl call org.freedesktop.UPower \
  /org/freedesktop/UPower/KbdBacklight \
  org.freedesktop.UPower.KbdBacklight SetBrightness i 0
sleep 2
cat /sys/class/leds/honor::kbd_backlight/brightness

busctl call org.freedesktop.UPower \
  /org/freedesktop/UPower/KbdBacklight \
  org.freedesktop.UPower.KbdBacklight SetBrightness i 2
cat /sys/class/leds/honor::kbd_backlight/brightness

На новых UPower также пробуем перечислить все keyboard-backlight objects:

busctl call org.freedesktop.UPower \
  /org/freedesktop/UPower \
  org.freedesktop.UPower EnumerateKbdBacklights 2>/dev/null || true

busctl tree org.freedesktop.UPower | grep -i KbdBacklight || true

Интерпретация:
- NativePath указывает на honor::kbd_backlight И SetBrightness 0/2 реально
  меняет клавиатуру -> UPower исправен, остаётся только KDE/PowerDevil cache;
- NativePath указывает на другой LED -> KDE управляет не нашим рабочим device;
- NativePath правильный, но SetBrightness падает -> смотреть journal UPower;
- DBus test работает, slider нет -> logout/login KDE после restart PowerDevil.

Версия UPower для диагностики:

upower --version 2>/dev/null || rpm -q upower
